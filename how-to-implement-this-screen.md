# How to implement screens on this device (ESP32-S3 + LVGL 8.4)

This board's display stack has a few sharp edges that aren't obvious from reading
LVGL's own docs. Three real bugs were found and fixed in this codebase by tracing
exact hang points with serial logging — this doc exists so the next screen doesn't
reintroduce them.

## 1. There is only ONE correct lock: `lvgl_port_lock()` / `lvgl_port_unlock()`

`bsp_display_start_with_config()` (called once in `setup()`) spawns its own
internal FreeRTOS task, `lvgl_port_task` (defined in `lv_port.c`), which calls
`lv_timer_handler()` in a loop forever. That task guards every call with
`lvgl_port_lock()` / `lvgl_port_unlock()` — a recursive mutex owned by `lv_port.c`.

**LVGL is not thread-safe.** Any other task that touches an `lv_obj_t` — creating
it, styling it, deleting it, reading its state — must go through that *same* lock,
or you get memory corruption that manifests as random hangs, partial screen
renders, or garbage on screen, all non-deterministically depending on timing.

This app used to have its own separate `SemaphoreHandle_t lvgl_mutex`, created in
`setup()` and used everywhere else. That was a second, *unrelated* lock — it did
nothing to protect against `lvgl_port_task` running concurrently. It "mostly
worked" by luck, until it didn't (this is what caused the "screen stuck on
Connecting" and "half-rendered payment screen" bugs).

**Rule:** never create your own mutex for LVGL. Always:

```cpp
if (lvgl_port_lock(0))       // 0 = wait forever (see lv_port.c: timeout_ms==0 -> portMAX_DELAY)
{
    // ... any lv_obj_*, lv_scr_load, lv_label_set_text, etc ...
    lvgl_port_unlock();
}
```

Use a short timeout (e.g. `lvgl_port_lock(10)`) only for opportunistic UI updates
where it's fine to skip a frame if the lock is busy (see `show_loading_spinner()`).

Also: don't call `lv_timer_handler()` yourself anywhere in the app. `lvgl_port_task`
already does it. `loop()` in `main.cpp` should stay basically empty — see the
comment left there for why.

## 2. Screen lifecycle: always create-new + `lv_scr_load()`, never mutate `lv_scr_act()` in place

Every screen-building function in this codebase follows the same shape:

```cpp
void create_some_screen(...)
{
    lv_obj_t *old_screen = lv_scr_act();
    lv_obj_t *screen = lv_obj_create(NULL);   // brand new screen object

    // ... build the whole UI tree under `screen` ...

    lv_scr_load(screen);                       // swap it in
    if (old_screen != NULL) {
        lv_obj_del_async(old_screen);          // see below for why async
    }
}
```

`create_main_payment_screen()` originally did `lv_obj_t *screen = lv_scr_act();
lv_obj_clean(screen);` instead — i.e. it reused and cleared the *currently
active* screen in place rather than swapping to a new one. This intermittently
left the display showing only partially-updated content (e.g. header drawn,
rest of the screen still black) after a WiFi reconnect. Stick to the
create-new-screen pattern for anything that replaces the whole screen; only use
`lv_obj_clean()`/in-place mutation for small, contained overlays (see
`show_loading_spinner()` and `show_result_screen()`, which add a temporary overlay
on top of the current screen rather than replacing it).

**Why `lv_obj_del_async()` and not `lv_obj_del()`:** several of these screen
functions get called *from inside an LVGL event callback of a widget that lives on
the screen you're about to delete* (e.g. tapping "ยกเลิก" calls
`clear_amount_event_cb` → `create_main_payment_screen()`, while LVGL is still
mid-dispatch of that very click event on the old screen). Deleting the screen
synchronously out from under an in-flight event callback is a use-after-free
waiting to happen. `lv_obj_del_async()` defers the actual deletion to the next
`lv_timer_handler()` pass, after the current event has finished dispatching —
safe from any calling context.

(Known pre-existing gap: `create_qr_payment_screen()` does not delete its
predecessor screen at all — see the README's "Known issues" section. Same fix
applies if you touch that function: capture `old_screen`, `lv_scr_load()`, then
`lv_obj_del_async(old_screen)`.)

## 3. Custom font `.fallback` fields — check them before mixing in `LV_SYMBOL_*`

`src/sarabun_20.c` and `src/sarabun_28.c` are generated by an LVGL font
converter from `Sarabun-Regular.ttf`, restricted to a Thai + basic-ASCII
codepoint range (see the `cmaps[]` table at the top of each file — ranges
32–126, 3585–3642, 3647–3675 for `sarabun_20`). They do **not** contain glyphs
for LVGL's built-in symbol icons (`LV_SYMBOL_RIGHT`, `LV_SYMBOL_OK`, etc.),
which live in a private-use-area codepoint far outside those ranges.

Both generated files had:

```c
.fallback = &sarabun_20,   // (or &sarabun_28) — points to ITSELF
```

When LVGL can't find a glyph in a font, it looks in `.fallback`. Here that
fallback is the same font — which also doesn't have the glyph — so it recurses
into itself forever. This is what caused the confirm button
(`"ยืนยัน  " LV_SYMBOL_RIGHT`, styled with `&sarabun_20`) to hang the entire
render task solid, every time that screen was built.

Fixed by pointing `.fallback` at a real font that has the LVGL symbol range —
a built-in Montserrat size already enabled in `lv_conf.h` works well:

```c
.fallback = &lv_font_montserrat_14,   // sarabun_20.c
.fallback = &lv_font_montserrat_24,   // sarabun_28.c
```

**If you regenerate these fonts** (e.g. adding more Thai characters, a new size)
with the LVGL font converter, check the `.fallback` line in the output before
using it — the converter seems to default this to a self-reference, and it will
silently work fine right up until you compose that font with a symbol icon in
the same label, at which point it hangs solid with no crash log and no useful
serial output before the hang.

**Rule of thumb:** any label mixing custom-font body text with an `LV_SYMBOL_*`
icon needs the custom font's `.fallback` to point somewhere that actually has
that icon. Built-in `lv_font_montserrat_*` fonts all include the full symbol
set, so they're the easy default fallback target.

## 4. Debugging a hang: what actually worked

A few things learned the hard way while chasing these bugs:

- **`pio device monitor` frequently misses the first ~10–20 lines after a flash
  or reset.** The upload's own hard-reset (or a manual RESET button press) can
  happen before the monitor process finishes opening the port, and PlatformIO's
  monitor does not replay history — bytes sent before it attached are gone.
  Chaining `pio run -t upload && pio device monitor` in one command narrows this
  window but doesn't eliminate it.
- **The most reliable capture method** was bypassing `pio device monitor`
  entirely and reading the port directly with `pyserial`, explicitly toggling
  DTR/RTS to force a clean reset right as the read loop starts:

  ```python
  import serial, time
  ser = serial.Serial('COM3', 115200, timeout=1)
  ser.setDTR(False)
  ser.setRTS(True)
  time.sleep(0.1)
  ser.setRTS(False)
  time.sleep(0.3)
  # now read — you get the ROM boot banner onward, every time
  ```

  This never missed a boot in testing, unlike relying on a physical RESET press
  into an already-open monitor session (which — on this board's native USB CDC —
  seems to lose the connection silently across the reset and never recover
  without restarting the monitor process).
- **Bisect hangs with checkpoints, not guesses.** When a function hangs with no
  crash and no watchdog reset, add a `Serial.println()` between every 3–5 lines
  and narrow down by binary search rather than reasoning about what "should"
  work. That's exactly how the font `.fallback` bug was found — reasoning about
  the code suggested nothing wrong with the confirm button; the checkpoint trace
  showed execution stopping dead between "btn_clear done" and "left panel done,"
  which pointed straight at the one thing that differed (the mixed symbol/font).
- Remove the checkpoint logging once you've found the bug — it's not free
  (extra flash space, extra serial noise), and it's easy to forget it's there.

## Quick checklist for a new full-screen UI

1. `lv_obj_t *old_screen = lv_scr_act();`
2. `lv_obj_t *screen = lv_obj_create(NULL);`
3. Build the tree under `screen`, wrapped in `lvgl_port_lock(0)` / `lvgl_port_unlock()`
   if you're not already inside a locked section (event callbacks from LVGL
   widgets are already running inside the lock — don't lock again there,
   `lvgl_port_lock` is recursive so it's safe either way, but no need).
4. If any label mixes a custom font with `LV_SYMBOL_*`, make sure that font's
   `.fallback` isn't self-referential.
5. `lv_scr_load(screen);`
6. `if (old_screen) lv_obj_del_async(old_screen);`
